# Prompts Context — Asistente de agendamiento por WhatsApp

## Proposito
Documenta el sistema de prompts del asistente. Es la fuente de verdad para editar contenido de prompts
(reglas de estilo, instrucciones por estado, descripciones de tools).

## Boundary: sistema vs perfil del profesional

El sistema es **profession-agnostico**. Nada en el codigo debe asumir psicologia, odontologia ni una
persona concreta:

- **Sistema** (este repo): flujo de agendamiento, estados, tools, reglas de estilo, formato de mensajes.
- **AgentProfile** (Firestore, por tenant): identidad del asistente, contexto profesional, servicios,
  tarifas, medios de pago, ubicacion del consultorio. Describe **quien es el profesional**, no **como
  funciona el workflow**.

Si una regla solo aplica a un profesional, va en su `AgentProfile`. Si aplica a todos, va en el codigo.

## Como se construye el system prompt

El system prompt **se genera**, no se escribe a mano. El profesional llena el formulario de perfil en la
UI (`PUT /v1/agent/professional-profile`) y el backend renderiza el XML y lo persiste en
`AgentProfile.system_prompt`.

```
Formulario UI  ──▶  AgentProfile (Firestore)
                          │
                          ▼
        professional_profile_xml_renderer.render(...)
                          │
         <identity> <professional_context> <services>
         <pricing> <payment_info> <style_rules> ...
                          │
                          ▼
              AgentProfile.system_prompt   ← base del prompt
```

- `professional_profile_xml_renderer.py`: funcion pura `AgentProfile -> XML`. Omite secciones vacias.
- `style_rules_template.py`: `<style_rules>` — reglas constantes para todos los tenants. Se parametrizan
  con `professional_address_term` (p. ej. "la Doc"); si esta vacio, cae a "la profesional".
- `professional_reference.py`: helper compartido que resuelve esa referencia en tercera persona.
  Lo usan `style_rules_template` y `state_instructions`.

Las `<style_rules>` **no** se exponen en la UI: las mantienen los desarrolladores.

En cada turno, el prompt final es:

```
AgentProfile.system_prompt
        │
        ▼
PromptAssembler.build_runtime_prompt()  (5 secciones, en este orden)
        │
        ├── RuntimeContextSection      ← estado, request_id, modalidad, fecha de cita, nombre
        ├── PatientProfileSection      ← datos conocidos del paciente (evita repreguntar)
        ├── OfficeContextSection       ← direccion, indicaciones de llegada, instrucciones virtuales
        ├── EnabledToolsSection        ← tools habilitadas este turno
        └── StateInstructionsSection   ← instrucciones especificas del estado
        │
        ▼
"### Runtime Context (Generated by Backend)"  ← lo concatena RuntimePromptBuilder
        │
        ▼
Prompt final enviado al LLM
```

Archivos del pipeline:
- `src/services/agentic/prompts/prompt_assembler.py` — ensambla base + secciones
- `src/services/agentic/prompts/prompt_section.py` — ABC para secciones
- `src/services/agentic/prompt_builder.py` — `RuntimePromptBuilder`, orquesta el build completo

## Los 8 estados de conversacion

Cada estado define que instrucciones recibe el LLM y que tools tiene habilitadas.
Instrucciones: `src/services/agentic/prompts/state_instructions.py`.
Whitelist de tools: `runtime_context_resolver.enabled_tools_for_state()`.

| Estado | Cuando aplica | Objetivo del LLM | Tools habilitadas |
|--------|---------------|------------------|-------------------|
| `NO_ACTIVE_REQUEST` | Sin request abierta | Iniciar agendamiento (o reagendamiento si hay cita previa). Con paciente recurrente se saltan las preguntas de identidad y se filtran servicios por `RETURNING` | `submit_consultation_reason_for_review`, `submit_reschedule_for_review`, `close_session`, `handoff_to_human`, `cancel_active_scheduling_request` |
| `AWAITING_CONSULTATION_DETAILS` | El profesional pidio mas detalle | Pedir detalles adicionales sin repetir la pregunta base | `submit_consultation_reason_for_review`, `handoff_to_human`, `cancel_active_scheduling_request` |
| `AWAITING_CONSULTATION_REVIEW` | Motivo enviado, pendiente de revision | Responder preguntas generales sin avanzar el flujo. Los acks cortos no son intent | `handoff_to_human` |
| `AWAITING_PATIENT_CHOICE` | Horarios propuestos | Interpretar la eleccion (por numero o descripcion) o el rechazo con preferencias | `select_proposed_slot`, `reject_proposed_slots`, `handoff_to_human`, `cancel_active_scheduling_request` |
| `COLLECTING_CONFIRMATION_DATA` | Slot seleccionado | Pedir los campos faltantes en UN mensaje y cerrar el agendamiento. En `RESCHEDULE` no pide datos: se heredan | `confirm_selected_slot_and_create_event`, `confirm_rescheduled_slot`, `handoff_to_human`, `cancel_active_scheduling_request` |
| `AWAITING_PAYMENT_CONFIRMATION` | Pago pendiente de aprobacion | Dar instrucciones de pago segun moneda/ubicacion, no repedir comprobante | `handoff_to_human`, `cancel_active_scheduling_request` |
| `AWAITING_ATTENDANCE_CONFIRMATION` | Recordatorio de asistencia enviado | Cerrar la confirmacion, o rutear a reagendar/cancelar segun claridad del intent | `confirm_attendance_received`, `submit_reschedule_for_review`, `handoff_to_human` |
| `POST_BOOKING_FOLLOWUP` | Cita reservada | Confirmar con fecha/modalidad exactas, dar direccion o instrucciones virtuales, cerrar sesion | `close_session`, `handoff_to_human` |

Fallback (estado desconocido): `handoff_to_human`, `cancel_active_scheduling_request`.

> `set_contact_name` está declarado en `ToolDefinitionRegistry` pero no aparece en ninguna whitelist,
> y el orquestador siempre filtra por `runtime_context.enabled_tool_names` — así que hoy **nunca llega
> al LLM**. El nombre del contacto se resuelve por otras vías (perfil del paciente / datos de la request).

### Alias de estados visibles al LLM

`RuntimeContextSection` proyecta alias para reducir la saturacion de attention con la palabra
"confirmation", que se filtraba al paciente en frases pre-pago ("para confirmarte la cita"):

| Estado canonico (codigo, Firestore, DTOs) | Alias visible al LLM |
|---|---|
| `AWAITING_PAYMENT_CONFIRMATION` | `AWAITING_PAYMENT_RECEIPT` |
| `COLLECTING_CONFIRMATION_DATA` | `SLOT_SELECTED_READY_TO_BOOK` |

`AWAITING_ATTENDANCE_CONFIRMATION` **no** se renombra: ahi la confirmacion es legitima (post-pago, el
paciente confirma asistencia).

### Datos inyectados en runtime context

`RuntimeContextSection` inyecta, cuando existen: `estado_conversacion`, `request_id_activo`,
`last_booked_request_id`, `request_status_activo`, `modalidad_actual`, `ubicacion_actual`,
`preferencia_horaria_actual`, `slot_seleccionado_actual`, `fecha_cita` (ya formateada en lenguaje
natural en la timezone del tenant), `nombre_paciente` y las notas del profesional para ese paso.

La timezone sale de `AgentProfile.identity.timezone` (IANA) con fallback a `America/Bogota`; el
`ReminderService` la usa igual para programar recordatorios. **Gap conocido**: el campo existe en la
entidad pero no en `AssistantIdentityDTO`, y `_identity_dto_to_entity()` no lo copia — así que guardar
el perfil desde la UI lo deja en `None` y todo cae al fallback. Solo tiene valor si se escribió
directamente en Firestore.

Regla transversal (`_NEVER_INVENT_INJECTED_DATA`): estos campos y los de "Datos del consultorio" son la
fuente unica de verdad y se usan **verbatim**. Si un campo no esta, no se menciona — nunca se inventa
una direccion, un piso ni una instruccion de llegada.

## Reglas de estilo

Viven en `style_rules_template.build_style_rules_xml()` y se inyectan en todo prompt renderizado:

- Presentacion en el primer mensaje usando `<assistant_name>` y `<professional>` de `<identity>`.
- Mensajes cortos (2-3 oraciones), tono de persona real por WhatsApp.
- Sin opinar ni empatizar sobre el motivo de consulta; sin agradecer de mas; sin "¡Perfecto!" repetido.
- Formato WhatsApp: `*negrita*`, bullets con `•`.
- Agrupar preguntas relacionadas en un mismo mensaje.
- No mencionar procesos internos, validaciones ni estados del sistema (cap `hides_internal_handoff`,
  formulada como regla conceptual, no lexica: el bot encuentra sinonimos para frases prohibidas).
- No inventar datos del paciente ni repreguntar lo ya dicho.

Regla de moneda (`_QUOTE_CURRENCY_PER_LOCATION`): si una tarifa tiene precios en varias monedas y no se
conoce la ubicacion del paciente, primero se pregunta donde reside; despues se cotiza **una sola**
moneda. Nunca varias juntas en el mismo mensaje.

## Archivos editables (boundary del agente Prompts)

### PUEDE editar
- `docs/sp.txt` — referencia local del system prompt en XML (ver seccion final)
- `src/services/agentic/prompts/state_instructions.py` — solo las listas de strings que retorna
  `_instructions_for_state()` (el texto, no la estructura del codigo)
- `src/services/agentic/prompts/style_rules_template.py` — el contenido de las reglas
- `src/services/agentic/tool_registry.py` — solo los valores `description=` de cada `FunctionDeclarationDTO`

### NO PUEDE editar (territorio del agente Backend)
- `prompt_section.py` (ABC), `prompt_assembler.py`, `prompt_builder.py`
- `runtime_context_section.py`, `enabled_tools_section.py`, `patient_profile_section.py`, `office_context_section.py`
- `professional_profile_xml_renderer.py` (estructura del XML)
- Cualquier archivo en `guards/`, `graphs/`, `tool_handlers/`
- `parameters_json_schema` y `name` en `tool_registry.py`
- `enabled_tools_for_state()` en `runtime_context_resolver.py`

## Herramientas de iteracion

- `scripts/prompt_lab.py`: renderiza y prueba prompts fuera del runtime, usando el mismo
  `enabled_tools_for_state()` que produccion.
- `make eval`: corre el framework de evaluacion (shapes + personas + juez LLM) y reporta que
  capabilities quedaron verificadas. Ver `docs/BACKEND_CONTEXT.md`, seccion "Evaluación".
- El dashboard `/evaluacion` del frontend muestra transcripts y veredictos por corrida.

## Testing

Despues de cualquier cambio de prompt:
- `uv run pytest tests/services -q`
- Para cambios en `state_instructions.py` o `style_rules_template.py`: revisar
  `tests/services/agentic/prompts/` y los tests que ejercitan el conversation graph.
- Validar que el texto suena natural en espanol y cumple las reglas de estilo.
- Para cambios de fondo, correr `make eval` y revisar que no bajen las capabilities verificadas.

## `docs/sp.txt`

Referencia local del system prompt en XML: sirve para ver el formato completo renderizado y para
redactar/iterar contenido fuera del runtime.

**Ningun codigo lo lee.** En produccion el prompt sale de `AgentProfile.system_prompt` en Firestore,
generado desde el formulario de perfil profesional. Para llevar un cambio de `sp.txt` al runtime hay
que subirlo con `PUT /v1/agent/system-prompt` — y tener en cuenta que la proxima vez que se guarde el
formulario, el renderer lo sobreescribe.
